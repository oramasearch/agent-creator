# agent-creator v0.2.0

**Released 2026-10-25. A minor release** (Steve named the version on 2026-10-25). One private image,
`docker.io/oramasearch/agent-creator:v0.2.0`, built on
[agent-runtime v0.2.0](https://github.com/oramasearch/agent-runtime/releases/tag/v0.2.0). Release
tracking: [agent-creator#16](https://github.com/oramasearch/agent-creator/issues/16).

Since [v0.1.0](v0.1.0.md), the Agent Creator Agent can read the methodology registry again, and its
tools are limited to exactly the reads a turn makes. Underneath, the agent-runtime it runs on carries
the 2026-10-21 security-review fixes. Everything v0.1.0 lists is otherwise unchanged: prompt v5, the
rule checks in `defects`, the turn answer, and how Lake reaches it.

What this changes for a person: methodology-bound proposals and declines pass their checks again,
and approved Pipelines that name a runnable methodology are offered for grants instead of being
listed as not runnable.

### From agent-runtime v0.2.0, underneath

The image is `FROM oramasearch/agent-runtime:${RUNTIME_TAG}` built with `RUNTIME_TAG=v0.2.0`, so it
carries every change in agent-runtime since its v0.1.0:

- [agent-runtime#19](https://github.com/oramasearch/agent-runtime/pull/19): `POST /v1/turn` compares
  the service token in constant time, and **refuses every turn with `503` when
  `AGENT_SERVICE_TOKEN` is unset or empty** (it used to be open). A wrong or missing bearer is `401`.
- [agent-runtime#21](https://github.com/oramasearch/agent-runtime/pull/21): **a turn's credential
  goes only to Lake at this service's `LAKE_URL`.** The turn's own `lake_url` is no longer read; with
  `LAKE_URL` unset or not an absolute http(s) address without user info, the turn is refused before
  any request goes out.
- [agent-runtime#26](https://github.com/oramasearch/agent-runtime/pull/26): dataset-confined agents
  are limited to qualified dataset reads (LSR-181). AgentCreator's work area is `workspace`, so its
  own turns are unaffected; an agent it proposes with work area `dataset` gets these limits (see
  *Known issues*).

### Settings it needs

No new setting of its own. agent-runtime v0.2.0 now **requires** `AGENT_SERVICE_TOKEN` and
`LAKE_URL` (and reads `AGENT_MODEL` when the record names no model; the record names `gpt-5.5`). The
Orama operator already renders `AGENT_SERVICE_TOKEN`, `LAKE_URL` and `AGENT_MODEL` for every library
agent, so no operator change has to roll first. A hand-run service without `AGENT_SERVICE_TOKEN` now
refuses every turn.

## What it does not include

Unchanged from [v0.1.0](v0.1.0.md#what-it-does-not-include):

- **It creates nothing.** Creating the approved agent is lake's (lake#233).
- **It does not change existing agents** ([lake#271](https://github.com/oramasearch/lake/issues/271)).
- **It proposes only what agent-runtime's twelve skills can do.**
- **It checks that Python compiles, not that it does the right thing.**
- **No live eval of the current prompt.** The only recorded eval is prompt v1 (15/16).
- **Conversation memory is per pod and in memory**; a restart loses it.

## Known issues

Security-relevant first.

1. **Workspace identity is not passed explicitly on every call**
   ([agent-creator#9](https://github.com/oramasearch/agent-creator/issues/9), with
   [agent-runtime#6](https://github.com/oramasearch/agent-runtime/issues/6)): App and build reads
   carry only `customer_id`, and the idle bus poll runs every 10 seconds. Related, in lake:
   [lake#918](https://github.com/oramasearch/lake/issues/918) (LSR-009, agent launch and schedule
   credentials escaping their workspace and inner action scopes).
2. **The runtime underneath keeps unbounded conversation histories and claims bus tasks before a
   worker is free** ([agent-runtime#25](https://github.com/oramasearch/agent-runtime/issues/25),
   LSR-076; [agent-runtime#24](https://github.com/oramasearch/agent-runtime/issues/24), LSR-075).
3. **Lake's shared agent service token** is accepted by every library agent, and a user's service
   launch holds it ([agent-runtime#14](https://github.com/oramasearch/agent-runtime/issues/14), on
   hold).
4. **The runtime still writes a trace per turn** under `TRACE_DIR` in the pod.
5. **Dataset-confined agents lose some reads** on agent-runtime v0.2.0
   ([agent-runtime#26](https://github.com/oramasearch/agent-runtime/pull/26)): index search, App and
   build reads, Pipeline and MCP tools are refused or omitted in `dataset` work areas. An agent
   AgentCreator proposes with work area `dataset` and a skill that needs those reads will not get them.
6. **The structured answer is shipped, the issue is still open**
   ([agent-creator#1](https://github.com/oramasearch/agent-creator/issues/1)), for lake's side to read
   `result`.
7. **The skills fixture is vendored** (`tests/fixtures/agent-runtime-skills.json`, from agent-runtime
   `cf964f4`). When agent-runtime's skills change, refresh it as `docs/methodologies/README.md` says.

## Where it has run

**The v0.2.0 tree has not run on the dev environment.** No `dev-<sha>` build of agent-creator ran on
the `dev` member of `lake-nonprod`; every Lake still takes the operator's default
`oramasearch/agent-creator:v0.1.0` (orama-operator `internal/controller/lake_defaults.go` on `dev`).
Moving it to `:v0.2.0` is a separate step, through testing (the e2e gate), staging and prod.
